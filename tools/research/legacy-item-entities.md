Состояние на 2026-10-20: в тестовом маршруте 775→340 реализовано отображение
обычных выпавших предметов. Серверные инвентарь, подбор и физика остаются общими.

## Реализованное представление

`legacy_entities.rs` хранит известные предметы одного соединения. `Session`
отдельно обрабатывает metadata собственного игрока и передаёт предметные пакеты
этому модулю. ID, UUID, количество и компоненты стека сохраняются существующим
кодеком предметов; предмет не заменяется произвольным совместимым видом.

| Native775 | Клиент340 | Преобразование |
|---|---|---|
| `0x01` Add Entity | `0x00` Spawn Object | Item71→Object2, objectData0→1 по наблюдению; позиция, углы и скорость |
| `0x63` Metadata | `0x3c` Metadata | Стек index8/type7→index6/type5; ограниченный набор общих полей |
| `0x65` Velocity | `0x3e` Velocity | LPVec3→три signed short; известный предмет либо собственный игрок |
| `0x23` Absolute Sync | `0x4c` Teleport, затем `0x3e` Velocity | Передаются положение и скорость, включая нулевую при остановке |
| `0x35` Relative Move | `0x26` Relative Move | Смещения 1/4096 без изменения единиц |
| `0x36` Move/Look | `0x27` Move/Look | Смещения и углы |
| `0x38` Look | `0x28` Look | Углы известного предмета |
| `0x7c` Collect | `0x4b` Collect | Предмет, собственный игрок-получатель, количество |
| `0x4d` Remove | `0x32` Remove | Список ID; удаление записи после проверки целого пакета |

Collect не удаляет запись: частичный подбор оставляет предмет в мире. Удаление
выполняется отдельным Remove. Повторный Remove неизвестного ID допустим;
собственный player ID нельзя удалить через предметную ветку. Повторный Spawn
занятого ID без Remove отклоняется.

Для metadata поддержаны флаги0, воздух1, отсутствие имени2, логические поля3–5
и стек8. Обычный sender ядра выдаёт только optional NoGravity5/type8 и
Stack8/type7; современные pose6 и frozen7 он не отправляет. Это отдельно
проверено по sender и тестам его фактической формы.

Состояние меняется после полного разбора пакета. Пределы реализации: 65 536
предметов и 1 MiB входного предметного payload. `Arc<BTreeMap>` позволяет
существующему `Session::control` клонировать состояние перед проверкой без
копирования всей карты при каждой телепортации или смене abilities.

Join очищает карту. Respawn в другое измерение также очищает её. Respawn внутри
того же измерения сохраняет карту, как существующий современный Tracker;
именно для клиента340 эта семантика ещё требует отдельного сетевого наблюдения.

Координаты хранятся в пространстве сервера; при выводе используется текущее
256-уровневое окно. Relative Move учитывает ту же сетку `round(coord*4096)`, что
`grid_of` нашего sender. Тесты включают отрицательные координаты и половинные
значения ±0.5/4096, ±1.5/4096. Они проверяют согласованность с собственным
sender, а не полную независимую проверку округления клиента.

## Оставшиеся границы

Не поддержаны другие типы сущностей и другие получатели Collect. Присутствующее
современное **имя сущности** отклоняется: старое строковое поле не должно
получить JSON вместо текста. Это не запрет имени предмета внутри ItemStack:
его обрабатывает существующий кодек компонентов.

Скорость за пределами ±3.9 по любой оси явно отклоняется до отдельной проверки
старого ограничения скорости. Распаковка LPVec3 также сохраняет погрешность
современной упаковки; полное совпадение с прямым старым encoder для всех скоростей
не установлено.

Выход предмета за текущее окно высоты возвращает ошибку. Предметы не скрываются
и не прижимаются к границе. Полное переключение окна должно согласованно
переотправлять чанки, сущности и телепорт игрока; здесь его нет.

Первая modes-проба не проверяла отдельные ненулевые Velocity, Absolute Sync и
живой Collect. Следующая отдельная проба закрыла эти случаи по значениям, но
обнаружила различия потока, описанные ниже. Не объявляются готовыми полная
поддержка340, физика всех сущностей или совместимость промежуточных версий.

## Живая проверка подбора и движения

Собственный [probe_legacy_item_pickup.py](../protocol-bridge/probe_legacy_item_pickup.py)
последовательно запущен на официальном340 (порт26025) и готовом core340 test
binary (26027), с двумя CPU и отдельной временной папкой для каждого сервера.
Ни Cargo, ни изменения Rust для этой проверки не потребовались.

Сценарий использует только работающие на обеих целях действия:

1. Подготовить площадку bedrock на Y63. На официальном сервере fill выполняется
   после загрузки чанков входом; на ядре — до входа в заранее созданном участке.
   Игрок стоит в `(0.5,64,0.5)`, координаты клиента ядра нормализуются окном−64.
2. Призвать bedrock3 в `(3.5,64.5,0.5)` с NoGravity1, проверить положение и
   количество. Телепортировать игрока к предмету; получить Collect3 с правильным
   player ID, ровно3 предмета в инвентаре и последующий Remove.
3. Очистить инвентарь, отвести игрока и призвать bedrock3 в `(3.5,74,0.5)` с
   обычной гравитацией. Проверить ненулевую скорость вниз, изменение позиции,
   приземление на Y64 и конечную скорость0. Предмет остаётся существовать.

На каждой цели **11 функциональных проверок прошли**; оба сервера завершились0.
Итоги совпали: pickup3, inventory3, конечная позиция `(3.5,64,0.5)` и скорость0.
Записи вне репозитория: `verification-legacy-items-final/pickup-official340-3`,
`pickup-core340`; сводка `pickup-comparison.json`. Проверяемые поля и сырые
entity packets сохранены в
[legacy-item-pickup.json](../protocol-bridge/testdata/legacy-item-pickup.json)
с SHA256 обоих полных исходных отчётов.

**Полная последовательность пакетов не совпала.** Скорости рядом с absolute
synchronization повторяются из-за преобразования native sync в два старых
пакета: Teleport и Velocity, дополнительно к обычному native Velocity. Это
повторная передача состояния, а не дополнительный шаг физики.

После посадки ядро также дважды отправляет вертикальные скорости−0.12 и0;
в этой официальной записи их нет. Однако фазы предметов различались:
официальный ID48 даёт остаток0 при делении на4, ID3 ядра — остаток3.
В собственном `Items::step_with_water` проверка опоры лежащего предмета идёт
раз в четыре такта по `(ticks+entity_id)%4`, а тяжесть накапливается между
проверками. Комментарий к этому коду ссылается на прежнюю пробу
`probe-item-rest`, наблюдавшую такие промежуточные скорости. Нынешний прогон
**не доказывает ошибку физики**: нужны выровненные фазы и отдельное наблюдение
текущей основной версии, определяющей общие игровые правила.

Промежуточный Y равен65.88293039264076 у ядра и65.88292959999313 у официального
сервера (разница около7.93e−7). Функциональный PASS подтверждает перечисленные
итоговые значения, но не точное совпадение физики, тайминга или packet stream.

Сохранены и две неудачные предварительные записи. В первой официальный fill
выполнялся до загрузки чанков, площадка не создалась и тестовый игрок был
отключён за зависание. Подбор при этом успел пройти. Во второй площадка была
верной, но падение с трёх блоков завершилось между сетевыми обновлениями:
сервер не отправил ненулевой Velocity. Поэтому высота поднята до10блоков.
В тестовом server.properties разрешён полёт, чтобы неподвижный собственный
сетевой клиент без симуляции движения игрока не отключался; физика предметов
выполняется самим сервером.

Motion NBT намеренно не задаётся. Наш `commands::summon_item` пока игнорирует
его и создаёт нулевую начальную скорость. Падение задаётся высотой и гравитацией.
Графический клиент, частичный подбор, reconnect и respawn этой пробой не
проверялись. Следующий шаг — выровнять фазы для сравнения движения, добавить контроль
основной версии и проверить оставшиеся случаи отдельно.
