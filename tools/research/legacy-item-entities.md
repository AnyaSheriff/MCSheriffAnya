## Реализованное представление

`legacy_entities.rs` хранит известные предметы одного соединения. `Session`
отдельно обрабатывает metadata собственного игрока и передаёт предметные пакеты
этому модулю. ID, UUID, количество и компоненты стека сохраняются существующим
кодеком предметов; предмет не заменяется произвольным совместимым видом.

| Native775 | Клиент340 | Преобразование |
|---|---|---|
| `0x01` Add Entity | `0x00` Spawn Object | Item71→Object2, objectData0→1 по наблюдению; позиция, углы и скорость |
| `0x63` Metadata | `0x3c` Metadata | Стек index8/type7→index6/type5; ограниченный набор общих полей |
| `0x65` Velocity | `0x3e` Velocity | LPVec3→три signed short; известный предмет либо собственный игрок |
| `0x23` Absolute Sync | `0x4c` Teleport, затем `0x3e` Velocity | Передаются положение и скорость, включая нулевую при остановке |
| `0x35` Relative Move | `0x26` Relative Move | Смещения 1/4096 без изменения единиц |
| `0x36` Move/Look | `0x27` Move/Look | Смещения и углы |
| `0x38` Look | `0x28` Look | Углы известного предмета |
| `0x7c` Collect | `0x4b` Collect | Предмет, собственный игрок-получатель, количество |
| `0x4d` Remove | `0x32` Remove | Список ID; удаление записи после проверки целого пакета |

Collect не удаляет запись: частичный подбор оставляет предмет в мире. Удаление
выполняется отдельным Remove. Повторный Remove неизвестного ID допустим;
собственный player ID нельзя удалить через предметную ветку. Повторный Spawn
занятого ID без Remove отклоняется.

Для metadata поддержаны флаги0, воздух1, отсутствие имени2, логические поля3–5
и стек8. Обычный sender ядра выдаёт только optional NoGravity5/type8 и
Stack8/type7; современные pose6 и frozen7 он не отправляет. Это отдельно
проверено по sender и тестам его фактической формы.

Состояние меняется после полного разбора пакета. Пределы реализации: 65 536
предметов и 1 MiB входного предметного payload. `Arc<BTreeMap>` позволяет
существующему `Session::control` клонировать состояние перед проверкой без
копирования всей карты при каждой телепортации или смене abilities.

Join очищает карту. Respawn в другое измерение также очищает её. Respawn внутри
того же измерения сохраняет карту, как существующий современный Tracker;
именно для клиента340 эта семантика ещё требует отдельного сетевого наблюдения.

Координаты хранятся в пространстве сервера; при выводе используется текущее
256-уровневое окно. Relative Move учитывает ту же сетку `round(coord*4096)`, что
`grid_of` нашего sender. Тесты включают отрицательные координаты и половинные
значения ±0.5/4096, ±1.5/4096. Они проверяют согласованность с собственным
sender, а не полную независимую проверку округления клиента.

## Оставшиеся границы

Не поддержаны другие типы сущностей и другие получатели Collect. Присутствующее
современное **имя сущности** отклоняется: старое строковое поле не должно
получить JSON вместо текста. Это не запрет имени предмета внутри ItemStack:
его обрабатывает существующий кодек компонентов.

Скорость за пределами ±3.9 по любой оси явно отклоняется до отдельной проверки
старого ограничения скорости. Распаковка LPVec3 также сохраняет погрешность
современной упаковки; полное совпадение с прямым старым encoder для всех скоростей
не установлено.

Выход предмета за текущее окно высоты возвращает ошибку. Предметы не скрываются
и не прижимаются к границе. Полное переключение окна должно согласованно
переотправлять чанки, сущности и телепорт игрока; здесь его нет.

Свежая modes-проба не проверяла отдельные ненулевые Velocity, Absolute Sync и
живой Collect: для них пока есть unit-покрытие и прежняя официальная запись.
Не объявляются готовыми полная поддержка340, физика всех сущностей или
совместимость всех промежуточных версий.

## Следующая минимальная живая проба

Сначала один предмет без гравитации и без начального Motion, затем отдельный
предмет с обычной гравитацией над поставленной площадкой:

1. На отдельных официальном340 и core340 серверах очистить инвентарь игрока,
   загрузить маленькую площадку из bedrock и выбрать точку в двух блоках от
   игрока. Для core перевести клиентский Y обратно через известное окно,
   дождаться подтверждения телепорта.
2. Summon bedrock3 с NoGravity1; проверить Spawn, metadata count3 и положение.
   Телепортировать игрока к предмету: проверить Collect count3 с правильным
   player ID, прибавление ровно3 в инвентаре и последующий Remove того же ID.
3. Убрать оставшиеся предметы, отвести игрока и призвать bedrock3 с обычной
   гравитацией на три блока выше площадки. Наблюдать падение и приземление:
   отдельную ненулевую скорость, изменение позиции и обновление остановки;
   проверить конечную высоту и отсутствие разрыва соединения. Сравнивать
   смысл значений с учётом окна/квантования, а не требовать одинакового такта
   для всей последовательности.

Текущую ветку `--entities` нельзя просто разрешить для core: она рассчитана
только на официальный340 и задаёт `Motion:[0.01d,0.0d,0.0d]`. Наш
`commands::summon_item` сейчас не применяет Motion и создаёт нулевую скорость.
Поэтому пробы должны использовать общий работающий способ — обычное падение —
либо сначала отдельно реализовать и проверить эту командную возможность.
Описанный следующий сценарий пока не запускался.
