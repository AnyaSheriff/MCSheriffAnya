# server.jar для обычного Minecraft-хостинга

Этот маленький Java launcher запускает родной сервер MCSheriffAnya в обычной
Java-панели, включая Pterodactyl. Нужны Linux x86_64, Java 17 или новее и
разрешение хостинга запускать программы из папки сервера. Зависимостей Java нет.

## Установка

1. Загрузите `dist/server.jar` в папку сервера (обычно `/home/container`).
2. Если нужно, в разделе запуска панели укажите имя JAR: `server.jar`.
3. Запустите сервер обычной командой панели, например:
   `java -Xms128M -Xmx512M -jar server.jar`.

При первом запуске launcher скачает из последнего GitHub Release архив
`mcsheriffanya-<tag>-x86_64-unknown-linux-musl.tar.gz`. Из архива берётся только
файл `mcsheriffanya`, остальные файлы хостинга не заменяются. Загрузка идёт во
временные файлы в той же папке; готовый бинарник заменяется атомарно.
Проверяются размер архива из API, заголовки tar, CRC gzip и непустой бинарник.
Если обновление не удалось, старый бинарник сохраняется, запуск завершается
ошибкой: следующий запуск может повторить обновление.

Можно сразу загрузить рядом с JAR готовый бинарник `mcsheriffanya` для Linux
x86_64 musl. Если он уже есть, launcher не обращается к сети без запроса
обновления. На запрете исполнения (`noexec`) он объяснит причину и завершится
с кодом 1. Понадобится помощь поддержки хостинга.

Первая строка лога: `MCSheriffAnya launcher 1.0.2`.
Для определения готовности в настройках панели используйте строку `Готово (`:
её выводит сам сервер после загрузки.

## Настройки и порты

Сервер читает `config/server.properties` и `config/mcsa.properties`, а не
`server.properties` в корне. Launcher создаёт папку и нужные файлы сам.

Если панель передала `SERVER_PORT`, launcher ставит в `config/server.properties`
`server-port=<SERVER_PORT>` и `server-ip=0.0.0.0`, сохраняя остальные строки.
Допустимый порт — от 1 до 65535. `SERVER_IP` не используется: внутри контейнера
сервер должен слушать все интерфейсы.

Если в `config/mcsa.properties` ещё нет `bedrock-port`, launcher добавляет
`bedrock-port=<SERVER_PORT>`. Java использует TCP, Bedrock — тот же номер по UDP.
Панель должна разрешать оба протокола. Уже заданный `bedrock-port`, включая `0`
(Bedrock выключен), сохраняется. При смене порта в панели проверьте и эту
настройку: автоматически меняется только Java-порт.

В сборке ядра с первоначальным выбором новая установка сначала просит указать
`java-version` и `send-error-reports` в `config/mcsa.properties`. Замените `choose`
предложенной версией и `true`/`false`, затем запустите снова. Созданная launcher-ом
заготовка конфига не отменяет этот выбор. Отчёты не отправляются без согласия.

Из корневого `server.properties`, который редактируют некоторые панели,
копируются только `motd`, `max-players`, `online-mode`, причём только если такого
ключа ещё нет в `config/server.properties`. Последующие изменения этих значений
делайте в `config/server.properties`. Другие строки и комментарии сохраняются;
разбор `key=value` соответствует самому серверу (UTF-8, без Java-экранирования).
Если `SERVER_PORT` не задан, launcher использует параметр JVM `-Dspt=<порт>`
(его передаёт Hosting-Minecraft.pro). При отсутствии обоих порты не меняются.

## Панель с отдельным ServerWrapper.jar

Для фиксированной строки запуска
`java ... -cp ServerWrapper.jar:server.jar pro.gravit.launcher.server.ServerWrapper`
загрузите `dist/ServerWrapper.jar` рядом с обычным `server.jar` хостинга.
В поле «Файл ядра» оставьте `server.jar`, а в списке флагов выберите
«Флаги под запуск лаунчера -cp ServerWrapper.jar:server.jar без проверки Forge 1.17+».
Порт берётся из `SERVER_PORT` или `-Dspt`, например `-Dspt=25951`.

Это собственный адаптер MCSA с именем входного класса из команды панели;
код Gravit не используется. Запускается MCSheriffAnya. Обычный JAR остаётся
для проверки панели по [инструкции хостинга](https://my.hosting-minecraft.pro/index.php?rp=/knowledgebase/119/).
Сам по себе этот режим не даёт разрешения выполнять программы, если хостинг
запрещает их запуск. Работу на конкретном тарифе нужно проверить запуском.

## Версия и обновление

Без настроек скачивается последний опубликованный выпуск. Чтобы закрепить
версию, задайте переменную окружения `MCSA_VERSION=v0.2.3-alpha` или добавьте
перед `-jar` параметр `-DMCSA_VERSION=v0.2.3-alpha`.
Параметр JVM имеет приоритет над переменной окружения. Версия влияет на скачивание;
существующий бинарник сам по себе не заменяется.

Для обновления остановите сервер, затем выберите один способ:

- Создайте пустой файл `mcsa-update` рядом с JAR и запустите сервер.
  После успешной установки launcher удалит этот файл.
- Задайте `MCSA_UPDATE=1` (или `-DMCSA_UPDATE=1`) и запустите сервер.
  Уберите эту настройку после обновления: иначе загрузка повторится при каждом запуске.
- Удалите `mcsheriffanya` и запустите сервер заново.

При обновлении действует `MCSA_VERSION`, если он задан. Если в выбранном выпуске
нет musl-архива, launcher покажет понятную ошибку. Можно выбрать другой выпуск
или загрузить бинарник вручную.

## Остановка и память

Ввод передаётся серверу через отдельный канал, вывод и ошибки — напрямую.
Поэтому даже в псевдотерминале панели ядро читает команды построчно и не
перерисовывает `> команда` после каждого символа. Это устраняет лишние строки
в веб-консоли и работает с уже выпущенным ядром, без замены бинарника.
Команда `stop` из панели доходит до родного сервера. Дополнительные аргументы
после `server.jar` передаются ему без изменений. При обычном завершении launcher
возвращает код завершения сервера.

При SIGTERM Java передаёт SIGTERM родному серверу и ждёт до 30 секунд, затем
принудительно завершает его. В `src/main.rs` обработчик SIGTERM ведёт в общую
остановку: выход игроков, остановка плагинов, сохранение всех трёх измерений и
табло, сообщение `Мир сохранён`. Панели следует дать больше 30 секунд на остановку.
SIGKILL нельзя обработать; при нём сохранение не гарантируется.

Java-часть небольшая (ориентир — около 30 МБ, фактическое потребление зависит от
JVM и скачивания). `-Xmx` ограничивает только Java-кучу, а не память Rust-сервера:
он работает отдельным процессом. Лимит RAM хостинга относится ко всему контейнеру.
Если панель позволяет, достаточно `-Xms16M -Xmx64M` для launcher; не стоит выделять
всю память контейнера Java. `SERVER_MEMORY` и `P_SERVER_UUID` launcher не использует.
Launcher не собирает телеметрию и не выводит значения окружения или секреты.

## Сборка и самопроверка

Из корня репозитория:

```sh
bash tools/jar-launcher/build.sh
java -jar tools/jar-launcher/dist/server.jar --launcher-self-test
java -cp tools/jar-launcher/dist/ServerWrapper.jar pro.gravit.launcher.server.ServerWrapper --launcher-self-test
```

Скрипт использует `/usr/lib/jvm/java-25-openjdk/bin/javac` с `--release 17` и
`jar` из того же JDK. Готовые одинаковые файлы:
`tools/jar-launcher/dist/server.jar` и `tools/jar-launcher/dist/ServerWrapper.jar`.
В манифесте задан `Main-Class: ru.sheriffanya.launcher.Launcher`.
Самопроверка не обращается к сети, не запускает сервер и не открывает порты:
проверяет маленькие архивы в памяти, обработку повреждений, JSON, адреса загрузки,
слияние настроек и выбор портов. Её временная папка удаляется после проверки.

Проверка консоли под Linux: `python3 tools/jar-launcher/test_console.py` из корня
проекта после сборки JAR. Она использует собственную заглушку ядра и настоящий
псевдотерминал: проверяет оба входа JAR, ввод порциями, UTF-8, CRLF, EOF, `stop`,
SIGTERM и код завершения. Сеть и игровые порты не используются.
