## Корова и ведро

Новый путь взрослой коровы с ведром использует существующую выдачу заполненного
ведра. Кормление, рост, золотой одуванчик и общий список наземных животных не меняются.
Мёртвый отправитель не допускается в новый путь. Вторая рука здесь не реализована.

13 ноября 2026 записан непрозрачный оригинальный сервер777: пять случаев,
семь фактических mainhand Use Entity. После обычного переподключения полный
инвентарь показал: одно ведро → одно молоко; повтор с молоком не меняет инвентарь;
телёнок не наполняет ведро; три ведра → два пустых и одно молоко; в творческом
режиме пустое ведро сохраняется, повтор не добавляет второе молоко.
Это наблюдения оригинала; совпадение кандидата проверяется отдельно.
Звуки, точные границы дальности и порядок всех пакетов этим не доказаны.

Кандидат `079a52d26fdd2dc46e77559601c048925a1a854a` проверен отдельно:
обычный Linux ELF SHA256
`586d7ca8bf5add723c2718128ec1096a2e828a9315793eda9cabd4015461012f`
совпал во всех пяти случаях и семи действиях. Сняты свежие полные инвентари;
для телёнка до действия положительно проверен флаг возраста в его сетевых
метаданных. Сервер завершился штатно. Вторая рука этим не проверялась.

## Старый клиент340

Разрешённая таблица protocol.json340 SHA256
`2dad4c918f6bd4492bfa8159b4db6ffbbf8f088b628258f03d437b0c0b760af9`:
Interact0 и InteractAt2 содержат руку, только InteractAt содержит три float;
приседание передаётся отдельным Entity Action. Сеанс хранит только полностью
принятые self-start/stop; невалидный пакет не меняет это состояние. Общая
упаковка новой точки взаимодействия сохраняет прежнее преобразование775.

Публичный вход340 остаётся закрыт. Новый host-тест проходит собственный Session
и настоящий обработчик кормления коровы; это не проверка входа настоящим1.12.2
клиентом и не заявление о полной совместимости. Сетевая проба с выдачей
пшеницы пока прерывается на неподдержанной форме пакета книги рецептов;
проверки взаимодействия до этого пакета не дошли.

## Меню Java-плагина

Наблюдение изменений выданного ItemStack отправляет обновление соответствующей
ячейки открытого меню. Клон/исходный аргумент setItem и заменённая старая ссылка
не подменяют актуальный предмет. Ядро ставит адресное уведомление зрителям
изменённого сундука; повторные уведомления объединяются. Подключение применяет
его только к тому же открытому экземпляру, сохраняя закрытое или заменённое окно.
Проверка в GitHub переводит собственный плагин
в WASM и использует один обычный ELF для нового SDK и старого ChestInventory.
Старый контроль должен дойти до той же GUI-проверки и показать ровно count1
вместо2; ошибка установки или запуска не засчитывается за регрессию.

Прогон GitHub Actions `43449519875` на указанном кандидате успешно прошёл:
новое окно сначала получило diamond2 с именем, затем diamond3 с новым именем
и stone4; emerald3 сохранился после изменения устаревшей ссылки. Следующий
вызов плагина подтвердил эти значения. Проверка состояния после перезапуска
прошла, но повторное открытие окна после перезапуска отдельно не записывалось.
Старый SDK на том же ELF дошёл до ожидаемой ошибки количества1 вместо2.
Проверки Clippy, сборки и обоих полных наборов Rust также прошли.

Тестовый клиент существующего GUI-набора —26.1. Этот набор не доказывает полную
совместимость Bukkit, выполнение произвольных плагинов или всю игровую логику.
