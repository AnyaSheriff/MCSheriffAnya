# Чёрный ящик: сверка с оригиналом по тактам

Робот заходит на официальный сервер 26.1.2 и на наш, строит одну и ту же
схему командами, нажимает рычаг как игрок и записывает всё, что сервер
присылает о мире: изменения блоков, действия блоков (ход поршня), звуки,
появление сущностей — с номером такта. Потом две записи сравниваются.

Правило: официальный сервер только **запускается** и наблюдается снаружи по
сети. Jar не распаковывается и не изучается. Единственное, что с него снято, —
таблица номеров звуков (`data/sounds.json`), его же штатным генератором
отчётов (`--reports`), это данные, не код.

Робот написан на [mineflayer](https://github.com/PrismarineJS/mineflayer)
(MIT, независимая реализация протокола) — библиотека берётся из
`~/node_modules`, в MCSheriffAnya её код не попадает.

## Запуск

Для основного26.3 `via_harness.py` запускает две отдельные копии серверов и
одинаковый внешний ViaProxy перед каждой. Код JAR не читается; используется
[документированный CLI](https://github.com/ViaVersion/ViaProxy#usage-for-server-owners-cli).
`--output DIR --binary FILE --jar FILE --proxy FILE --port 26170 SCENARIO…`
задают пути и шесть локальных портов26170–26175; JAR ViaProxy закреплён3.4.14.
`--repeat 3` проверяет шум, `--names FILE` берёт JSON-массив имён.
Штатные `bot.js` и `compare.js` не меняются; `via_ticks.js` добавляет Client
Tick End через `physicsTick` обеим сторонам и обнаруживает ранний обрыв.
Без `--proxy`, с `--primary 26.1.2`, тот же запуск проверяет обычный маршрут775.
Пары, журнал сравнения, SHA и итоги сохраняются в DIR; `--wire` дополнительно
пишет оба направления сетевого потока перед сервером, без изменения пакетов.
`--official-recordings DIR` повторяет только нашу сторону по сохранённым
официальным JSON, не запуская официальный сервер повторно.

```sh
tools/blackbox/setup.sh            # один раз: скачать server.jar, eula, настройки, права роботу
cd tools/blackbox/vanilla && java -Xmx1G -jar server.jar nogui   # оригинал на порту 25566
tools/blackbox/run-ours.sh         # наша сборка на порту 25567 (нужен cargo build)
node tools/blackbox/compare.js piston-lever --record             # записать обе стороны и сравнить
```

Отчёт печатается и кладётся в `reports/<сценарий>-<дата>.md`. Без `--record`
сравниваются последние записи.

## Сценарии

`scenarios/*.json`: `blocks` — что поставить (координаты относительно
площадки), `actions` — что делать (`click` — нажать как игрок, `set` —
командой setblock) и через сколько тактов, `record_ticks` — сколько писать.
`align` — начать действия в такте, кратном этому числу по возрасту мира
(датчик света пересчитывается раз в 20 тактов, и без привязки фаза
пересчёта относительно команды у каждой записи своя).

## Удар по блоку: `dig`

`{"after": N, "dig": [dx, dy, dz]}` — пакет Player Action «начал копать» по
блоку площадки. В выживании мгновенные блоки (посевы, трава, цветы) ломаются
сразу и роняют урожай (сценарии `farm-*`).

## Полосы: несколько роботов разом

Полный прогон по одному сценарию шёл час. Сценарии друг от друга не
зависят, поэтому их можно писать разом — каждый своим роботом на своей
площадке: `node compare.js <сценарий> --record --parallel --lane N`.

- Полоса N — робот `blackboxN` (полоса 1 — прежний `blackbox`) и площадка
  на `512·(N−1)` блоков дальше по x. Дальность обзора у обоих серверов —
  4 чанка, так что блоки, звуки и сущности одной полосы до робота другой не
  доходят. Полоса 1 стоит на прежнем месте: старые записи сравнимы.
- В командах сценария координаты — только через `$(dx,dy,dz)`, а имя
  робота — через `$(bot)`: `tp $(bot) $(3.5,0,0.5)`, `clear $(bot)`.
  `@e[…]` — с `distance`, иначе команда заденет чужую площадку.
- Права роботам полос выдают `run-ours.sh` и `setup.sh` (ops.json), а на уже
  запущенных серверах — `node lanes.js op 25566 25567`.
- `node lanes.js plan` делит сценарии: что можно писать разом, а что только
  по одному. По одному идут помеченные `"exclusive": true` (время суток,
  молния), сценарии со своим местом `origin` (оно задано ради самого места,
  полоса его не сдвигает) и те, чьи команды меняют мир целиком: `time`,
  `weather`, `gamerule`, `@a`, `@e` без `distance`. Причина пишется рядом.

Прогон полосами — `bb-run-lanes.sh` (рядом с `bb-run-par.sh`, вне
репозитория): пять полос берут сценарии из общей очереди, самые долгие
первыми, потом исключительные — по одному, полосой 1.

## Как робот попадает в такт

Нажатия расставляются по тактам сервера, а не по часам робота: `after`
в сценарии — это такты от первого нажатия. Чтобы знать, где у сервера
начинается такт, робот делает две вещи.

Во-первых, сверяет часы по пакету «обновление времени»: он приходит раз
в секунду и несёт возраст мира, значит каждый такой пакет говорит, когда
у сервера был такт ноль. Первый пакет приходит при входе, вне общего
порядка, и врёт на сотни миллисекунд — такие измерения отбрасываются;
из остальных берётся самое раннее, наименее задержанное.

Во-вторых, калибруется: «обновление времени» оригинал шлёт в одном месте
такта, мы — в другом, поэтому одна лишь сверка часов даёт у каждого свой
сдвиг, и робот целился бы в середину такта у одного и на границу у другого.
Поэтому перед записью робот шесть раз нажимает вхолостую и смотрит, в какую
долю сетки приходят ответы: отклик уходит сразу, как сервер его обработал,
то есть в начале такта. Граница счёта ставится на полтакта от этих приходов —
тогда события ложатся в середину такта, дальше всего от края, — а нажатие
уходит в середину настоящего такта сервера.

Само нажатие робот шлёт пакетом сам: у mineflayer `activateBlock` сперва
плавно поворачивает голову и ждёт своего физического такта, а это до 50 мс.

## Мобы: `track_mobs`

Со `"track_mobs": true` в сценарии робот пишет и мобов площадки (корова, свинья,
овца, курица): появление и свойства, каждый пакет движения, скорости, событий
и поворота головы, а также урон, звуки, анимации и атрибуты (строка `text`), и
свойства выпавших из них предметов. Призывать надо действием `cmd` (`summon cow
$(3.5,0,3.5) {NoAI:1b}`), чтобы появление попало в запись. Действия `attack` и
`interact` бьют и щёлкают по последнему появившемуся мобу, а с `"which": N` — по
N-му по порядку появления. `NoAI:1b` призванный висит на месте и стоит; `data
merge entity @e[type=cow,limit=1] {NoAI:0b}` включает его на время падения.
Высота площадки — 8 блоков: выше мобы для робота не видны.
`MOB_TYPES` включает и врагов (зомби, скелет, крипер, паук) и стрелы: у стрел
пишутся появление, сверка места, скорость при остановке и уход. Враги с ИИ
идут за роботом сами — такие сценарии (`zombie-attack`, `skeleton-arrow`,
`spider-climb`) случайны по старту и сверяются правилами `count` с `anytick`;
точные сценарии — `NoAI` (`zombie-hit`, `skeleton-stand`, `creeper-explode`).
Солнце жжёт только на высоте площадки 5 (`origin`, как у `daylight-*`):
у нашего ровного мира на −59 неба нет.

Слежение оригинала идёт раньше хода сущностей, поэтому конец такта показывает
мобов такими, какими они были до хода (`Items::mob_view`), а звуки их хода (плита
под свиньёй) идут после (`WorldEvent::Tracker`).

## Драка игроков: второй робот (`second`)

Со `"second": true` в сценарии заходит ещё один робот — `<имя первого>b`
(`blackboxb`, у полосы N — `blackboxNb`), в командах он `$(bot2)`. Ничего сам
не записывает: действует по строкам сценария с `"bot": 2`, а пишет первый.
Обычно первый — жертва, второй — нападающий: жертва пишет всё, что сервер
шлёт ей самой (`track_self`: здоровье, ушиб, скорость, атрибуты, смерть), и
всё, что видит о втором как о чужом игроке (`track_players`: взмахи, свойства,
события, снаряжение, звуки). `track_second` пишет и то, что получает второй
(строки `b: …`).

- Действия с `"bot": 2`: `attack` (бьёт первого), `control` (`forward`,
  `sprint`…), `look` (`[yaw, pitch]`), `hotbar`, `use`, `release`; `cmd`
  всегда идёт от первого. Первый бьёт второго действием `attack` с
  `"target": "second"`. У `use` и `release` есть `"hand": 1` — вторая рука
  (щит); без него — основная.
- В `setup`: `!look2 yaw pitch`, `!sprint2`, `!nosprint2`, `!hotbar2 N`,
  `!hotbar N` (ячейка панели у первого).
- Ставить бойцов надо командой: `tp $(bot) $(3.5,0,3.5) 180 0` (yaw 180 —
  лицом к −z), `tp $(bot2) $(3.5,0,1.5) 0 0` (лицом к +z). Оба в выживании
  (`gamemode survival $(bot)`), у первого `!stopfly`.
- Сценарии с двумя роботами трогают правило игры (`natural_health_regeneration`),
  поэтому помечены `"exclusive": true`.

## Зонды падения: `track_client_moves`

`"track_client_moves": true` дополнительно пишет точные исходящие пакеты
`position`, `position_look`, `look`, `flying` обоих роботов (`a: sent` и
`b: sent`), включая признак земли, и входящую скорость без округления
(`velocity exact`). Это диагностические строки: они нужны для вывода
правил сброса падения и фазы приземления, а не для послаблений в сравнении.
Зонды `fall-mode-teleport-motion` и `pvp-mace-landing-motion` следует записать
дважды на vanilla 26.1.2, затем на нашей сборке. Существующие сценарии без
этого флага сохраняют прежний формат.

## Как читать таблицу

Такты считаются от первого ответа сервера на нажатие. Задержка отклика
показана отдельно рядом с действием. Пометки: «у нас позже/раньше на
N», «нет у нас», «лишнее», «порядок в такте другой». Высота звука случайна и
не сравнивается; `[пачкой]` — блоки пришли одним сообщением.

## Окно записи

Запись идёт до такта `record_ticks + 10` от первого действия включительно.
События такта приходят в его середину — туда, где раньше кончалось ожидание,
и последний такт то попадал в запись, то нет (у `minecart-slope` сдвиг
вагонетки на +150 был у одного сервера и пропадал у другого). Поэтому робот
слушает ещё три такта сверх окна и пишет само окно в запись (`window`), а
`compare.js` отбрасывает всё позже его конца — у обеих сторон одинаково.

## Такты внутри шага и задержка отклика

Нажатие робота приходит на сервер в случайное место такта, поэтому такты
событий в шаге считаются от первого отклика сервера, а сама задержка
отклика показывается в заголовке шага: «первый отклик через X / Y такт.».
Она сверяется отдельно: разница в один такт считается дрожью сети, больше —
сдвигом («отклик у нас позже на N»), он входит в «Сдвинуто по тактам».
Иначе опоздавший целиком отклик прятался бы: события внутри шага совпали бы.

## Случайное у оригинала: поле `random`

Часть поведения у оригинала случайна сама по себе: запал динамита от
взрыва, сила взрыва вагонетки, цвет нот проигрывателя, всплески выпавших
предметов, гаснущая на случайном такте руда. Такое нельзя сравнить один
в один — два прогона оригинала расходятся между собой. Поэтому:

1. Сперва сценарий по возможности делается неслучайным. Пример: у динамита
   пол — обсидиан; в каменном полу край воронки случаен (сила каждого луча
   умножается на 0,7…1,3, а сам динамит при поджоге сносит вбок), а так
   взрыв рушит только слабые блоки рядом, и они сверяются точно.
2. Что осталось случайным, объявляется в сценарии полем `random` — списком
   правил. Общих поблажек нет: правило действует только в своём сценарии,
   и у каждого есть `why` — цитата вики или замер «оригинал против
   оригинала». Всё, что правило не задело, сверяется точно, с тактом.

Виды правил (подробно — в `compare.js`, у `applyRandom`):

- `values` — поле случайно, но из известного набора (`values`) или
  промежутка (`range`): цвет ноты, сила взрыва. Такт и остальное — точно.
- `delay` — случайная задержка от события `from` до `to` (запал) в пределах
  `range`; всё после `to` сверяется точно относительно `to`. События
  ожидания (`between`, например отсчёт запала) без пары — в допуске.
- `mask` — случайная часть ключа заменяется (`pattern` → `replace`):
  урон вагонетки от взрыва случайной силы.
- `count` — события случайны целиком (всплески, семена из травы):
  сверяется число, оно должно лежать в `range`; с `anytick` не сверяется и такт.
- `anytick` — событие в случайный такт или вовсе без него (руда гаснет
  по случайному такту); у нас все такие события одного блока — в один такт.
- `jitter` — то же событие (ключ целиком), но такт дрожит на `max` тактов
  (частицы эффектов от команды на +0 или +1); без пары — промах, как обычно.

В отчёте совпадение по допуску помечено «случайное, в допуске: <правило>»,
а перед итогом стоит строка «Случайное, в допуске: N (входит в «Совпало»)».
Итоговая строка «Совпало: … Сдвинуто по тактам: … Нет у нас: … Лишнее у
нас: …» прежняя, допущенное входит в «Совпало». Если сам оригинал вышел за
допуск, отчёт пишет «Внимание: …» — правило надо пересмотреть.

Проверить правило на самом оригинале: записать его дважды и сравнить
записи между собой — `node compare.js <сценарий> --files a.json b.json`
(или `--record --ours-port 25566`). Запись без сравнения:
`node bot.js 127.0.0.1 25566 scenarios/<сценарий>.json a.json`.

## Что нашли и починили этим инструментом

Сценарии `piston-lever`, `sticky-pull`, `double-push`, `grass-crush`,
`repeater` сходятся с оригиналом полностью (единственное расхождение —
случайные семена из травы, оно и у оригинала случайное).

- маленькие пакеты копились в ядре на 40 мс (алгоритм Нейгла) — отключено;
- звук шёл после сообщения о ходе, у оригинала — до;
- у рычага не было звука щелчка и повтора блока после щелчка;
- пакеты игрока применяются в начале такта, а всё, что случилось за такт,
  уходит клиенту в его конце; несколько изменений в одной секции —
  одним сообщением;
- изменения, которые делает ход поршня (признак «выдвинут», опустевшие
  и раздавленные места, блоки в конце хода), уходят на такт позже хода;
  раздавленное место уходит служебным блоком «движущийся поршень»;
- при вытягивании опустевшее место уходит сразу, при толкании — нет;
- трава без ножниц даёт семена в одном случае из восьми, а не себя;
- поршень, у которого пропал запланированный такт, зависал навсегда: над ним
  оставался невидимый служебный блок, а голова пропадала. Теперь такой ход
  возвращается в очередь и доигрывается.

Сценарий `piston-pulse` (наблюдатель даёт поршню импульс в два такта, питание
пропадает посреди хода) тоже сходится с оригиналом полностью.

Сценарий `piston-fast` (рычаг дёргается каждые три такта, новое питание
приходит, пока ход ещё идёт) раньше шатался и для сверки один в один не
годился: робот попадал нажатием в разные такты. После привязки нажатий
к тактам сервера он сходится полностью — и по дороге нашлось ещё два наших
расхождения с оригиналом:

- такт отсчитывался от пробуждения (`MissedTickBehavior::Delay`), поэтому
  опоздание на пару миллисекунд копилось и сетка тактов уезжала; теперь
  `Skip` — потерянное пропускается, сетка держится;
- «обновление времени» рассылалось раз в секунду по часам соединения,
  из-за чего приходило то через 20 тактов, то через 21; теперь, как
  в оригинале, каждый двадцатый такт мира.

### Рыбалка и карты

`track_fishing: true` пишет движение и свойства поплавков. С
`reel_on_bite: true` робот один раз подсечёт при получении свойства 9
(`biting=true`); действие `reel_on_bite` попадёт в журнал. Это не допуск
на случайность: время ожидания и добыча всё равно сравниваются буквально.
Сначала нужны независимые записи оригинала, чтобы обосновать допуски.

`track_maps: true` пишет Map Data: масштаб, блокировку, значки,
прямоугольник обновления и байты цветов в hex. Номера карт нормализуются
по порядку первого появления, поскольку счётчики сохранённых миров различны.

## Основной26.3: собственный клиент777

`record777.py` использует сетевой клиент `tools/protocol-bridge/probe_gameplay.py`
для обеих сторон. Нужны закреплённые `candidate-json` и непрозрачный официальный
JAR; ни сторонний protocol codec, ни распаковка JAR не используются:

```sh
python3 tools/blackbox/record777.py --data /path/to/candidate-json \
  --jar /path/to/server.jar --binary target/release/mcsheriffanya \
  --output tools/blackbox/reports/combat777-run
python3 tools/blackbox/analyze777.py tools/blackbox/reports/combat777-run \
  --protocol /path/to/candidate-json/protocol.json
```

По умолчанию сначала выбираются40боевых сценариев из задания: `pvp-*`,
`cow-crit*`, `sword-sweep-*`, `itemaudit4-knockback*`, `*shield*`. Имена после
параметров задают другой явный список. Оригинал занимает26140/26141, ядро —
26142; `--core-only --core-port 26144` повторяет только ядро по сохранённому
оригиналу. Серверам выделены отдельные папки, у ядра `java-version=26.3`;
оригинал получает `/dev/null` и завершается по своему PID. `--resume`
переиспользует официальные записи; `--skip-recorded-core` также сохраняет
уже снятое ядро. Сырые записи сохраняются до очистки и никогда не коммитятся.

`--isolate-vitals` выравнивает начальные здоровье/еду обоих игроков смертью
и ждёт Respawn/положительное здоровье; уже объявленная в setup смерть повторно
не добавляется. Начальная ячейка панели —0, явный `!hotbar` в setup её меняет.
Это устраняет зависимость
от длительности мирного лечения между сценариями; действия и RNG не меняются.
`--core-debug` сохраняет подробную причину ошибки протокола в частном логе.
Lookup звуков777 снимается обычными consumable.sound для всех прежних имён.
Частные серверы пробы используют `allow-flight=true`, чтобы проверка полёта
не обрывала запись при ограниченной физике клиента.

`--version 775` проверяет тот же путь на основном26.1.2: нужны его
закреплённые protocol/items/blocks/entities JSON и официальный JAR26.1.2.
`--parallel` пишет обе стороны одновременно; `--official-port` меняет26140.
Сетка физики общая для обоих игроков; фаза атрибутов берётся из полученных
пакетов, а при повторе ядра сохраняется фаза официальной записи.

Сырые пакеты декодируются нашими средствами и проходят настоящие обработчики
`bot.js` через `replay777.js`; результат сравнивает неизменённый `compare.js`.
Поэтому `track_*`, первый/второй наблюдатель, округления, ключи, задержки и
правила `random` сценария совпадают с исходным ящиком. Заметки о порядке
сохраняются отдельно: исходный итог `compare.js` не включает их в счётчики.
Имена атрибутов777 уточняются закреплёнными Slot-наблюдениями; звуки — обычным
предметом `stone[consumable={sound:...}]`, с сохранением исходных Slot bytes.

Поддержаны `window_click` с актуальными window/stateId и release-use5/6 для
775/777. Подготовительные появления сущностей сохраняются для слежения.
Калибровка использует тот же порог3/6 и круговую фазу, что `bot.js`.
Ограничения: сухая каменная площадка; полной физики мира/коллизий нет.
Многотактовые пачки движения пока дают явный decoder gap. Ошибки часов,
соединения и декодера не считаются совпадением; отчёты остаются untracked.

## Способности и повторный вход

`abilities-check.py` использует только стандартную библиотеку Python и сетевые
пакеты protocol775/777 (номера из закреплённого JSON), без библиотек протокола.
Для777 передаётся `--protocol 777`; учитываются Configuration known-packs,
новое подтверждение переноса и Client Tick End раз в50ms. Незнакомые ID777
игнорируются до сопоставления обработчиков775: граница мира0x2c777 не KeepAlive.
Регрессии dispatch: `python3 tools/blackbox/test_abilities_check.py`.
Официальный 26.1.2 из `vanilla` запускается на свободном порту 261xx;
наша сборка — в отдельном каталоге и на другом свободном порту. Робот
`blackbox` должен иметь права оператора; вход без авторизации.

```sh
python3 tools/blackbox/abilities-check.py 26141 --output /tmp/abilities-vanilla.json
python3 tools/blackbox/abilities-check.py 26142 --output /tmp/abilities-ours.json
diff -u /tmp/abilities-vanilla.json /tmp/abilities-ours.json
```

Зонд сравнивает каждый пакет Player Abilities целиком: флаги, обе скорости,
число и порядок пакетов. Проверяются творческий полёт с повторным входом,
вход без полёта, восстановление полёта наблюдателя после запроса остановки,
запрещённый запрос в выживании, переходы между всеми четырьмя
режимами, повторная установка текущего режима, сохранение полёта при смене
измерения и сброс после смерти.
Команды ждут ответа сервера, поэтому загрузка измерения не перемешивает шаги.
Зонд меняет режим и положение только своего робота и завершает его сессию.

Эталонный захват 26.1.2: `fixtures/abilities-26.1.2.json`.
