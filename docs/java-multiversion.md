# Java 26.2 / 26.3 и собственная совместимость версий

Рабочая ветка: `migration/java-26.3`. Это начало разработки, **не поддержка входа
клиентов 26.2/26.3**. Основной протокол ядра пока 775 (26.1.2).

## Проверенные сведения

Официальный [список выпусков Mojang](https://piston-meta.mojang.com/mc/game/version_manifest_v2.json)
на 18 октября 2026 указывает последний стабильный выпуск 26.3. Описания:
[26.2](https://www.minecraft.net/en-us/article/minecraft-java-edition-26-2),
[26.3](https://www.minecraft.net/en-us/article/minecraft-java-edition-26-3).
Снапшоты 26.4 не входят в эту работу.

Разрешённая таблица [protocolVersions.json](https://github.com/PrismarineJS/minecraft-data/blob/master/data/pc/common/protocolVersions.json):

| Версия | Протокол | Data version |
|---|---:|---:|
| 26.2 | 776 | 4903 |
| 26.3 | 777 | 5023 |

При проверке [dataPaths.json](https://github.com/PrismarineJS/minecraft-data/blob/master/data/dataPaths.json)
полных таблиц для 26.2/26.3 ещё нет. Проверка воспроизводится командой
`python3 tools/protocol-bridge/audit.py`; исходные URL и SHA-256 сохранены в
`tools/protocol-bridge/audit-2026-10-18.json`. Номера пакетов, реестры блоков/вещей и форматы
компонентов нельзя вывести только из номера протокола. Для переноса нужны
разрешённые спецификации/JSON и измерения на оригинальном сервере.

## Что заложено

`tools/protocol-bridge` — наша библиотека без чужих реализаций. Версия клиента
отделена от внутренней версии ядра и сохраняется при передаче чтения Play
отдельной задаче. Допуск пока разрешает только родную версию; известный номер
нового клиента не открывает неподдерживаемый вход.

Есть двустороннее сопоставление числовых ID по полному имени ресурса, с отказом
при неизвестном ID, отсутствующем имени или неоднозначной таблице. Для пакетов
дополнительно проверяются фаза соединения, направление и полная разрешённая
схема полезной нагрузки. Совпадение внешнего имени типа недостаточно.

`translate_id` переводит только номер пакета и не разрешает пересылку содержимого:
вложенные реестры, block states, metadata, компоненты вещей, NBT, команды и чанки
нуждаются в отдельных переводчиках. Игровой поток пока не вызывает эти заготовки.

## Следующие этапы

1. Получить разрешённые таблицы/измерения 26.2/26.3; зафиксировать их источник и
   контрольные суммы. Сравнить Login, Configuration, Play и динамические реестры.
2. Реализовать направленные адаптеры между соседними версиями. Сначала вход,
   конфигурация, пустой мир/чат, затем чанки, вещи/инвентарь, сущности и бой.
3. Для нового клиента к старому ядру обеспечить семантику старого мира; для
   старого клиента к новому явно определить видимые замены новых объектов.
   Нельзя безусловно заменять предметы в командах/крафте/действиях клиента.
4. Проверять отдельные клиенты каждой версии: вход, смена измерений, инвентарь,
   взаимодействия, PvP, разрыв/повтор входа. Старые точные боевые проверки сохранить.
5. Включать маршрут лишь после реализации и проверки всей обязательной цепочки.
   Обновление ядра до новой версии отдельно требует новых игровых механик/контента.

Код ViaVersion, ViaBackwards, прокси, протокольных библиотек и Mojang не читался
и не используется. Проверка исходящих ID должна происходить до сжатия/шифрования,
входящих — после расшифровки/распаковки. В этом этапе обходов этих границ нет.

## Проверка первого этапа

18 октября 2026: `cargo test --release --workspace` — 2483 теста ядра,
4 теста библиотеки перевода и 11 тестов seedmap прошли (69+2 ignored).
`cargo clippy --release --all-targets --workspace -- -D warnings` и release build
прошли. `smoke.py --binary <путь>` проверил 9 сетевых условий на отдельном
порту: native LoginSuccess, отказ 774/776/777/778, ответы Status с честной версией
775 для четырёх вариантов Handshake. Это проверка границы допуска, не проверка
игры клиентами новых версий и не замена black-box сверки механик.

## Выбор основной версии и первый запуск

`java-version` в `config/mcsa.properties` хранит выбранную основную версию.
При первом создании файла сервер пишет в консоль текущую версию и место её
настройки. Перед открытием порта/мира значение проверяется.

**Сейчас эта ветка поддерживает только `java-version=26.1.2`.** Значения 26.2,
26.3 и опечатки останавливают запуск с понятным сообщением. Это предохранитель
на время разработки, а не готовое переключение между игровыми версиями.
Нельзя менять только номер Handshake/Status и выдавать это за перенос.
Переход существующего мира на старую версию требует отдельной совместимости
его данных и резервной копии; автоматического downgrade пока нет.

## Измерение официального 26.3

`observe.py` запускает официальный JAR как непрозрачную программу в отдельном
временном каталоге на 127.0.0.1:26003. Проверяет SHA-1, наблюдает Status, Login,
Configuration и первый пакет Play. JAR не распаковывается инструментом,
реестры/датапаки/данные мира не выгружаются. Сохраняются ID, длина и хеш пакета,
а для явно согласованных Known Packs — их имена и версия.

Записи для оригинальных 26.1.2 и 26.3 находятся в
`tools/protocol-bridge/observations-2026-10-18.json`:

| Наблюдение | 26.1.2 | 26.3 |
|---|---:|---:|
| Протокол в Status | 775 | 777 |
| Login Success, ID | 2 | 2 |
| Login Success, длина тела для McsaProbe | 27 | 43 |
| Known Packs, ID | 14 | 15 |
| Пакет после последних реестров, ID | 13 | 14 |
| Finish Configuration, ID | 3 | 3 |
| Первый пакет Play, ID / длина тела | 49 / 112 | 50 / 113 |

Login Acknowledged, ответ Known Packs и подтверждение Finish Configuration
из нашего старого сценария были приняты. Их полной эквивалентности это не
доказывает. Дополнительные байты Login Success и смысл новых полей Play пока
не установлены. Пакет после реестров соответствует позиции Update Tags,
но его новый формат ещё не разобран. Следующий этап — разрешённые таблицы и
проверка форматов, затем весь игровой путь. Включать 26.3 по этим нескольким
наблюдениям нельзя.

Настройки двух офлайн-режимов описаны в [offline-mode.md](offline-mode.md).
