# MCSA Guard

Дополнительный закрытый модуль парольной авторизации Java. Публичный репозиторий
[AnyaSheriff/MCSA-Guard](https://github.com/AnyaSheriff/MCSA-Guard) содержит только
документацию и подписанные готовые выпуски. Исходники модуля не входят в ядро.

В `config/mcsa.properties`:

```properties
auth-enabled=true
auth-provider=guard
```

Guard действует при `online-mode=false`. Настройка `auth-premium` продолжает
управлять проверкой лицензии Java. Bedrock использует отдельную авторизацию Xbox
Live: Guard её не меняет. Первый выпуск поддерживает **Linux x86_64** (включая
musl и glibc); для других платформ запуск с Guard завершается понятной ошибкой.
Встроенная авторизация остаётся доступной по умолчанию (`auth-provider=builtin`).

При старте ядро загружает описание выпуска, проверяет Ed25519-подпись встроенным
открытым ключом, платформу, протокол, номер выпуска, размер и SHA-256 бинарника.
Новый выпуск не может иметь номер меньше установленного. Описание и подпись
сохраняются одной атомарной операцией. При недоступности обновления используется
проверенный кэш. Без доверенной копии ядро не запускает парольную авторизацию.

Начиная с ядра **v0.2.7-alpha**, доступ к `/proc` не требуется (в v0.2.6-alpha
он использовался для запуска).

На Linux проверенные байты помещаются в запечатанный `memfd`: подмена файла
после проверки не меняет запускаемый код. Запуск через `execveat(AT_EMPTY_PATH)`
не требует `/proc`, доступа к чужим процессам или root. Хостинг должен разрешать
`memfd_create`, запечатывание памяти и `execveat` для дочернего процесса.
Если хостинг запрещает такой запуск,
Guard завершится ошибкой; небезопасного резервного запуска с диска нет.
Сервис работает локально через приватные каналы stdin/stdout, без TCP-порта.
Пароли не передаются GitHub или разработчику и не добавляются в аргументы процесса.
Одновременно выполняется одна проверка, остальные получают сообщение о занятости.
Лимит времени операции — 10 секунд; зависший процесс завершается.

## Аккаунты и резервная копия

Пароли существующих аккаунтов проверяются старым способом и переводятся в Guard
после успешного входа. UUID, имя, операторские права и мир сохраняются. Новые
пароли и смена пароля сразу используют Guard. Старый хеш удаляется из записи.
В базе применяется версия 2: старое ядро отвергнет её вместо обхода проверки.
При наличии защищённых аккаунтов переключение на `builtin` запрещено.

Секрет установки создаётся в `mcsa-guard/pepper`, отдельно от `auth.db`, с правами
доступа только владельцу процесса. Он сохраняется между обновлениями и никогда
не встраивается в распространяемый файл. Потеря или подмена секрета не включает
упрощённую проверку. Нужна резервная копия **обоих**: `auth.db` и каталога
`mcsa-guard/`, с ограничением доступа. Не публикуйте их и не отправляйте в отчёты.
При восстановлении верните согласованную пару из резервной копии.

## Границы защиты

Обфускация усложняет изучение программы, но не гарантирует секретность её
устройства. Стойкость паролей не опирается на секретность алгоритма. Слабые пароли
всё равно опасны. Отдельный секрет помогает при утечке одной базы; при полном
захвате сервера атакующий может прочитать секрет или перехватить новый пароль.
Подпись работает, пока ядро и его встроенный открытый ключ доверенные. Замена
ядра позволяет отключить проверку. Локальная защита от отката также не является
защитой от полного восстановления злоумышленником старого состояния всего хоста.

Ключ подписи выпусков хранится только на ПК разработчика. Его нет в ядре,
плагине, публичном репозитории и GitHub Actions. Смена доверенного ключа требует
обновления ядра; отдельного механизма удалённого отзыва в первом выпуске нет.
