# Основа планирования зависимых областей

2026-11-16, собственные исходники baseline `f33a502d0e4db59ebf9b52c256463dc986157489`.

`src/parallel_regions.rs` — самостоятельный планировщик с проверками. Сейчас его
подключает **только** `tests/parallel_regions.rs`; игровой такт его не вызывает.
Это подготовка границ владения, **не ускорение runtime**, не полный parallel AI и
не включение нового режима. Новых потоков, настроек, зависимостей Cargo и unsafe нет.
Описание или код чужого серверного ядра для этой реализации не использовались.

## Что делает план

Входной массив `Task` уже находится в прежнем последовательном порядке. У задачи
есть уникальный `u64` ID и либо полный объявленный набор `Access::Read/Write`, либо
`Footprint::Unknown`. Все значения ID, включая 0 и MAX, допустимы; дубликат — ошибка,
в том числе при принудительном последовательном режиме. ID не задаёт порядок.

Ключи ресурсов типизированы: чанк/сущность с ключом мира, очередь заявок жителей
этого мира, общая случайность, выдача номеров сущностей, порядок видимых эффектов.
Координаты сравниваются точно, без умножения, расстояния или переполнения на краях.
Ключ мира — внутренний `u32`, не новый сетевой registry ID.

Если две задачи обращаются к одному ресурсу и хотя бы одна пишет, они попадают в
одну компоненту. Связи транзитивны: общий ресурс третьей задачи соединяет две
дальние области. Чтение общего неизменяемого снимка само по себе не соединяет
задачи. В каждой компоненте остаётся исходный порядок. Компоненты перечисляются
по индексу первой задачи; их внутренний порядок не зависит от численных ID или
порядка перечисления ресурсов. Повторные доступы объединяются, запись сильнее чтения.

`Unknown` соединяет **все** задачи, включая задачи других миров и чистые задачи.
`Policy::ForceSerial` делает то же; будущий вызывающий код обязан выбрать его при
активных плагинах/непроверенном вмешательстве. Здесь нет автоматического чтения
состояния плагинов и нет утверждения, что произвольный Known достоверен.

Результат хранит `Stamp { tick, epoch }`, полные входные описания и политику.
`Plan::validate` отвергает другой такт, epoch, политику, порядок/состав задач или
описания ресурсов. Смена описания владения замечается даже без нового epoch.
План пересчитывается из текущих входов: исчезнувшая зависимость позволяет split,
сохранённой таблицы старых владельцев нет. Цена — хранение копии описаний.

После барьера координатор передаёт результаты `TaskResult` в `Plan::collect_results`
вместе с текущими входами. Рабочее задание записывает ID и stamp при запуске.
Сборщик повторно проверяет план и отклоняет устаревшие результаты, чужие ID,
повторы и пропуски. При успехе возвращается весь буфер в исходном порядке задач,
даже если компоненты завершились в обратном порядке или их задачи чередовались
во входе. Этот порядок предназначен для последовательного применения эффектов
координатором. Вход остаётся замороженным до конца применения, а работники
только вычисляют значения. Координатор повышает epoch при изменении входа или
владения, в том числе при повторном использовании тех же ID.

## Чего этот контракт не доказывает

**Declared не означает проверенную полноту.** Планировщик не анализирует World,
вызовы, скрытые caches, замки, очереди и RNG. Полноту списка и отсутствие его
изменений после validate обязан обеспечить владелец входа; для runtime нужен
барьер/эксклюзивное владение, а не только сравнение числа epoch. Между видами ключей
нет неявного покрытия: операция с сущностью, занятостью чанка и эффектами обязана
перечислить все эти ресурсы. Неизвестный transitive доступ требует Unknown.

Расстояние и соседство чанков не используются как доказательство. Связь через
редстоун, воду, поршень, инвентарь, scheduled tick или команду должна войти в полное
замыкание доступов; пока такого извлечения нет, механизм остаётся Unknown.
Порядок видимых событий требует Write(OrderedEffects), кроме отдельно доказанного
буферизованного протокола с прежней последовательной публикацией. Одной сортировки
готовых эффектов недостаточно, если вычисление читало изменяемое состояние.

Полный `step_all_with_executor` остаётся связанным: `src/mob/mod.rs` передаёт
общий mutable RNG в `mob.tick`, расширяет `claimed` жителей и вызывает выдачу ID;
`src/tick.rs` создаёт снаряды и применяет эффекты после AI. Эти задачи пока Unknown
либо имеют общие Write(GlobalRng/EntityIds/OrderedEffects) и не разделяются.
Никакого `unsafe Sync` для World, замены RNG на seed моба или immediate-wait
переноса полного шага на другой CPU здесь нет.

## Проверки

16 Rust tests, команды для проверки:

```sh
cargo test --release --test parallel_regions
cargo clippy --release --all-targets -- -D warnings
```

Проверяются empty/pure входы, дубликаты, read/read, writer bridge, дальняя
транзитивная связь, разные миры/виды ключей, общие RNG/IDs/effects/claims, Unknown,
ForceSerial, нормализация доступов, устаревшие входы и split на новом такте.
Три регрессии проверяют восстановление порядка чередующихся задач после обратного
завершения групп, точное покрытие задач результатами и отклонение устаревших
результатов при повторном использовании ID.
Первый исчерпывающий тест перебирает 6561 граф четырёх задач с двумя ресурсами и
сравнивает с независимым попарным графом/транзитивным замыканием. Второй на тех же
6561 входах сравнивает итоговое состояние **и наблюдённые чтения** модели с serial
при обратном завершении компонент. Отдельный отрицательный пример доказывает,
что незаконная перестановка зависимых операций меняет эту модель.
Это проверки алгоритма, не реальные игровые/ванильные сценарии и не замер TPS.

## Следующий небольшой шаг

До настоящего исполнителя нужен проверяемый extractor для **одной** реальной
фазы. Безопасный интеграционный опыт — отдельный тест полного текущего шага мобов:
подать реальные задачи как Unknown, получить одну компоненту и вызвать неизменённый
serial шаг в исходном порядке; сравнить полное состояние, очереди, RNG continuation
и next_entity_id со старым вызовом. Это докажет привязку порядка, но не ускорит шаг.
После этого выделять Known можно только для профилированной самостоятельной фазы
с неизменяемым снимком и доказанным полным footprint; существующий pure sensing
уже имеет свой ordered executor и не считается новой находкой.

Будущий исполнитель использует прежний общий actual-tick >50ms/next-tick бюджет,
ленивые helpers, serial fallback и барьер перед зависимыми фазами. Наличие двух
компонент само по себе не является разрешением создать ещё один пул потоков.
