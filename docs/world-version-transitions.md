# Смена основной версии мира

Техническое решение от19октября2026 по требованиям владелицы. Это проект
реализации, **не готовая возможность текущей сборки**. Сейчас основная версия
по-прежнему26.1.2; незавершённые профили не предлагаются при первом запуске.

Читающая проверка `src/world/profile.rs` подключена к запуску через
`src/world/startup.rs`: строгий ограниченный манифест, сравнение профилей
и отпечаток таблиц блоков/предметов. Неподходящий манифест останавливает запуск
до создания каталогов мира и слушателей. Отпечаток не покрывает все данные
мира. Добавлен отдельный внутренний механизм снимка папки мира; полный анализ,
подключение снимка к смене игровой версии и конвертер ещё нужны. Пользовательской
команды пока нет. При обычном запуске снимок теперь используется только перед
описанным ниже обновлением собственного формата хранения.

На Unix процесс удерживает соседний `.mcsa-world.lock` до завершения runtime.
Файл остаётся на месте после выхода, но системная блокировка освобождается
при закрытии процесса. На остальных платформах пока выполняется только
читающая проверка с предупреждением: исключительный доступ не обеспечен.
Мир без манифеста продолжает прежний путь запуска; автоматически создавать
манифест или объявлять его исходный профиль распознанным эта проверка не будет.

## Профиль сервера и сохранение

Один игровой движок использует выбранный профиль правил. Общие таблицы хранятся
один раз, различия версий — отдельными наборами данных и обработчиками изменённых
правил. Версия клиента выбирает только сетевое представление этого мира.

`config/mcsa.properties:java-version` задаёт желаемый профиль. Будущий
`world/mcsa-world.json` хранит фактический профиль, версию собственного формата,
идентификатор реестра сохранённых объектов и идентификатор снимка мира. Профиль
выбирается по явному каталогу поддержанных релизов, не сравнением строк версий.

Существующие `.mcs` содержат числовые состояния. До замены реестра они читаются
только прежней таблицей, затем переводятся по имени и свойствам объекта. В новом
формате палитра сохранения хранит имена/свойства, а числовые ID остаются локальными
индексами палитры и значениями в памяти. Аналогично переводятся предметы и
компоненты. Неизвестный ID — ошибка с адресом, а не воздух или пустой инвентарь.

Номер раскладки региона и playerdata не доказывает основную версию игры.
Старый мир без манифеста допускается к переносу только после распознавания
поддержанного исходного формата и реестра. Неоднозначный источник блокирует
переход с объяснением; настройка желаемой версии не разрешает угадывание.

## Точка входа и исключение одновременной записи

Проверка перехода выполняется до `World::open`, загрузки игроков/плагинов,
создания слушателей и запуска фоновых писателей. Существующий `World::open`
уже меняет файлы и переносит старые регионы, поэтому вызывать его для проверки
совместимости нельзя: нужен отдельный читающий обход сохранения.

Реализованный внешний замок находится рядом с миром, вне переименовываемой
папки. На Unix его держит весь процесс сервера, включая обычную игру; создание
нового мира тоже требует этой блокировки. Старые `session.lock` измерений
сохраняются. Внешний замок сам по себе не исключает запись прежней сборки,
которая о нём не знает, и не разрешает копирование работающего мира.
Внутренний механизм снимка удерживает существующие `session.lock` всех трёх
измерений во время копирования. Это совместимость только с прежними сборками
**нашего ядра**, которые используют тот же `flock`; взаимное исключение
с официальным сервером или другими приложениями не подтверждено. Общий этап
перехода версии с удержанием этих замков до конца конвертации ещё не подключён.
На платформах без надёжной блокировки переход останется недоступным.

## Реализованный внутренний снимок папки мира

`src/world/snapshot.rs` предоставляет внутренние `create_verified_backup`
и `verify_backup`. Это копирование и проверка файлов, а не распознавание
содержимого мира или разрешение понизить его версию. Вызов требует живой
`StartupGuard` того же каталога. Пока нет команды backup, автоматического
вызова при смене версии, восстановления, очистки старых копий и конвертации.
Неподдержанные основные версии по-прежнему недоступны.

Копируется весь каталог мира: все существующие измерения, playerdata,
неизвестные и скрытые файлы, временные файлы и пустые каталоги. Имена Unix,
которые не являются UTF-8, сохраняются без потерь. Внешние auth/config/plugin
базы и другие файлы за пределами мира в снимок **не входят**. Полнота папки
не доказывает сохранение игрового состояния, которое ещё не записано на диск.

До создания копии проверяются существующие замки измерений, полный перечень
файлов, ограничения памяти/глубины и свободное место. Отсутствующий lock
существующего измерения и неизвестная схема измерений дают отказ. Символические
и жёсткие ссылки, специальные файлы, вложенные mount/bind-mount, xattrs/ACL,
особые permissions и несовпадающее владение пока также дают явный отказ.
Они не пропускаются молча. Запись или исправление исходных файлов не выполняются.
Читающие дескрипторы используют `O_NOATIME`; обычное внешнее чтение без него,
изменившее atime во время копирования, тоже может вызвать отказ проверки.

Снимок создаётся в соседней папке
`backups/<world>/<random-id>.partial/world`, вне исходного дерева. Потоковая
копия ограничена по памяти; сохраняются bytes, обычные права, uid/gid и mtime,
atime записывается как архивное значение. Для каждого файла вычисляется
SHA-256, а записанные байты перечитываются отдельно. `files.jsonl` содержит
полный перечень и метаданные; `snapshot.json` — завершённый манифест и hash
самого перечня. Эти hashes проверяют целостность, но не являются подписью.

После полной повторной проверки, сброса файлов/каталогов и повторной сверки
исходника папка переименовывается без перезаписи существующего final, затем
сбрасываются родительские каталоги. При ошибке `.partial` сохраняется для
диагностики. Ошибка после rename до подтверждённого parent sync отмечается
отдельно: публикация могла состояться, слепой повтор недопустим. Проверка final
заново сверяет manifest, каждый hash/размер/метаданные, полноту дерева и
привязку имён к проверенным файлам. `.partial` не принимается как готовый снимок.

Реализация пока только для Linux с доступными `openat2`, `renameat2`, `flock`,
`O_NOATIME` и нужными операциями файловой системы. Старые ядра Linux, seccomp
или файловая система могут запретить их: небезопасного запасного пути нет.
Другие ОС возвращают Unsupported. Исходный мир и соседняя копия должны быть
на одном mount; это не обещание поддержки любой панели хостинга.

Замки advisory: они согласуют работу нашего runtime и прежних наших writers,
но не запрещают произвольному процессу того же пользователя/root менять пути.
Проверки inode и metadata обнаруживают изменения на границах операции;
после возврата caller должен сохранять исключительное владение копией.
`StartupGuard` остаётся у caller, а замки измерений освобождаются после create.
В узком обновлении хранения они удерживаются непрерывно до публикации
манифеста/записи допуска. Полная будущая конвертация игровых профилей
должна отдельно продлить их удержание на весь переход.

Прошёл 21 тест на собственных временных файлах: полнота трёх измерений,
playerdata, ссылки/special, ограничения, занятые и заменённые locks, ошибки
записи/проверки, подмена partial/final и аварийное завершение отдельного
дочернего процесса. Также прошли 6 тестов startup и 7 тестов profile.
Полный release suite: 2773 прошли, 83 ignored, 0 ошибок. Эти результаты получены
до механической правки Clippy: разбиение заранее проверенного чётного числа
hex-байтов заменено с `chunks_exact(2)` на `as_chunks::<2>().0`.
После этой эквивалентной правки повторно прошли все 21 snapshot-тест
(229,27 с вместе с компиляцией), all-target Clippy с `-D warnings` (24,03 с)
и release build (101,84 с). Полный suite после замены итератора не повторялся;
единственное изменение исходников подтверждено сравнением файлов.
Child-exit завершает только собственный контролируемый процесс и не моделирует
физическую потерю питания или неисправность накопителя.

## План: резервная копия и проверка перехода

При понижении сначала сохраняется полный исходный снимок. При повышении,
требующем изменения файлов сохранения, используется такой же порядок.
Папка бэкапа — соседняя `backups/<world>/<migration-id>.partial`, никогда
не внутри копируемого мира. Копируются все измерения, регионы, игроки,
инвентари, эндер-сундуки, контейнеры, сущности и очереди действий.

Копирование потоковое, с ограниченной памятью и одним рабочим потоком.
Для файлов записываются размер и SHA-256; после записи проверяется содержимое
копии, сбрасываются данные и каталоги. Завершённый манифест и переименование
`.partial` публикуют готовый бэкап. Жёсткие ссылки не используются: изменение
рабочего файла не должно менять копию. Символические ссылки и специальные
файлы требуют явного поддержанного обработчика; обход за пределы мира запрещён.

До копирования оценивается дополнительное место для бэкапа, рабочей копии
и запаса конвертации. Эта оценка не заменяет обработку ошибок записи:
закончившееся место, ошибка чтения или проверки останавливают переход,
оставляя исходный мир действующим. Неполный бэкап не подходит для отката.

Читающий обход проверяет блоки и свойства, предметы и компоненты, сущности,
измерения и диапазоны высот, контейнеры, игроков, очереди тактов и структуры.
Отчёт содержит суммарные количества и ограниченное число примеров с адресами,
чтобы миллионы неподдержанных блоков не исчерпали память. Нельзя обрезать мир
до старой высоты, удалять новые предметы или менять их клиентскими заменителями.

Данные плагинов внутри папки мира включаются в снимок, но их простое
копирование не доказывает совместимость. Известные внешние хранилища требуют согласованного обработчика
снимка/перехода; при его отсутствии смена профиля отказывает до активации.

## Конвертация и восстановление после сбоя

Преобразование пишет соседнюю `world.migration-<id>` на том же файловом разделе.
В ней переводятся все данные, затем выполняются повторное чтение, проверка
ссылок и сверка количества сохранённых объектов. Игровой сервер на этой копии
не запускается. Новый манифест профиля создаётся только для проверенного результата.

Журнал перехода вне папки мира содержит идентификаторы исходного/целевого
снимков, пути и состояния `prepared`, `validated`, `activating`, `committed`.
Каждое состояние сохраняется атомарно со сбросом на диск. После `validated`
пишется `activating`, исходная папка переименовывается в `world.previous-<id>`,
а проверенная — в `world`. После сброса каталога записывается `committed`.
Два переименования сами по себе не считаются одной атомарной операцией.

При следующем запуске журнал читается **до создания отсутствующей world**.
По идентификаторам снимков проверяется, где находится каждая копия. Если
сохранился подтверждённый результат, активация завершается; иначе возвращается
исходный снимок. Неоднозначность или повреждение требуют остановки, а не
выбора папки по времени изменения. Бэкап и прежняя папка автоматически
не удаляются при успешном переходе. Восстановление возвращает весь снимок,
без смешивания позднейших инвентарей со старыми сундуками.

## Генерация после повышения

Каждый сохранённый чанк получает идентификатор генератора и его настроек.
Существующие чанки сохраняют блоки, постройки и происхождение. Новые используют
целевой генератор; сохранённые семя и тип мира остаются прежними.

Для проверенных пар генераторов согласование рельефа работает только на новой
стороне границы. Оно использует неизменяемые граничные данные старых чанков;
результат должен быть одинаков при разном порядке загрузки и числе потоков.
Граница фиксируется по набору чанков до перехода: появившийся после перехода
чанк не становится новой исходной границей для соседей. Иначе загрузка мира
в разном порядке меняла бы результат генерации.
Нельзя считать верхнюю постройку игрока природным рельефом: для старых сохранений
без нужных данных применяется отдельно проверенный консервативный переход,
а неизвестная пара генераторов не получает обещание гладкой границы.

Запись структуры проходит через проверку происхождения чанка: новая генерация
не меняет уже существующие чанки. Нельзя публиковать частично вырезанную
структуру: её размещение должно целиком помещаться в допустимой новой области.
Расширение мира по высоте и изменение биомов — отдельные переходы формата,
не повод перегенерировать существующие постройки.

## Порядок реализации и приёмка

1. Манифест, каталог профилей и проверки источника без изменения данных.
2. Общая блокировка, проверяемый полный бэкап и восстановление журнала.
3. Читающий анализ совместимости и проверенные преобразования конкретных пар.
4. Происхождение чанков и переходы между конкретными генераторами.
5. Включение выбора профиля только после проверки игровых правил и сохранения.

Обязательны тесты сбоя на каждом шаге записи/переименования, нехватки места,
повреждённого бэкапа, чужой блокировки, неизвестного ID и данных плагина.
Проверяются все измерения и инвентари, отсутствие потери/удвоения предметов,
неизменность старых чанков и одинаковые границы при разных порядках генерации.
Неподдержанная пара должна завершаться до запуска игры и изменения исходника.

## Курсор игрока: формат playerdata v10

Формат v10 добавляет отдельную ограниченную запись курсора, сохраняя его
количество и компоненты даже при полностью занятом инвентаре. Чтение прежних
версий1–9 сохранено; у них курсор отсутствует. Формат инвентаря/чанков этим
изменением не меняется. При обычном выходе остаётся прежний возврат предметов
из курсора, а после сбоя сохранённый курсор восстанавливается отдельно.

**Старое ядро с читателем v9 не понимает v10.** Возвращаться на него с новым
playerdata нельзя: старый код считает неизвестный формат нечитаемым и входит
с пустыми данными. Для отката нужна совместимая полная резервная копия.
Автоматического преобразования10→9 нет.

Это исправление сохранения курсора, не общая транзакция игрока/сундука/мира.
Раздельные записи и несохранённые выброшенные сущности остаются отдельными
задачами. Проверка манифеста теперь подключена к запуску, но не обеспечивает
автоматический согласованный снимок всех измерений или атомарный перенос.
Внутренний снимок описан выше; подключение к смене версии ещё предстоит.

## Отказ при неизвестном формате сохранения

Читатель native-чанков различает повреждение и несовместимость. Неизвестная
версия раскладки или состояние блока, отсутствующее в текущем каталоге,
останавливают загрузку этого чанка. Он не заменяется новой генерацией,
не помечается как повреждённый и не записывается поверх исходных данных.
Прежняя политика восстановления известного повреждённого формата сохранена.

Перенос старого региона `.rcw` сначала проверяет версии всех целых записей.
Неизвестная версия запрещает перенос всего региона до записи `.mcs` или
отложенных повреждённых данных. Пока неперенесённый `.rcw` остаётся без `.mcs`,
загрузка отсутствующих чанков этого региона также не запускает генерацию.
Для уже существующего `.mcs` сохранён прежний приоритет над `.rcw`.

Полный заголовок `MCPD` с неподдержанной версией playerdata останавливает
вход Java и Bedrock до создания нового состояния игрока. Это узкая защита:
чужая подпись, обрезанный заголовок, повреждение известного формата и ошибки
чтения всё ещё обрабатываются по прежним правилам. Не все вложенные ID вещей
и компонентов проверяются на совместимость.

Эти отказы не заменяют предварительную проверку всего мира и не включают
новый игровой профиль. Автоматическое понижение версии по-прежнему недоступно.

## Хранение предметов мобов: chunk v5 и playerdata v11

Новые записи чанков имеют версию5; прежняя версия4 продолжает читаться.
Playerdata пишется с версией11 и читает1–11, включая курсор, появившийся
в версии10. Внешняя раскладка региона остаётся1. Это изменение нашего
формата хранения, а не смена основной версии Minecraft или реестра.

Версионное дополнение записи моба сохраняет полные товары жителей, предмет
и количество во рту лисы, предмет панды, груз и нестандартное количество
экипировки испытаний. Старое тело записи читается прежним способом, новые
поля восстанавливаются из ограниченного дополнения. Неизвестная схема,
обрезанная запись, непредставимые компоненты и чужие каталогу предметы
дают отказ до записи. Чанк с неподдержанными мобами или содержимым улья
не заменяется сгенерированным. Проверка вложенности общая для предметов,
контейнеров, ульев и находящихся внутри пчёл. Попугаи на плечах игрока проверяются как полные записи попугая,
включая вложенные предметы; хвост неизвестных байтов не отбрасывается.

На Linux известный манифест с прежней раскладкой playerdata10 обновляется
до11 только после полной проверенной копии. Игровой профиль и реестр
остаются прежними. Копирование и атомарная публикация нового манифеста
проходят при непрерывном удержании всех существующих замков измерений.
Сбой до публикации не разрешает начать запись нового формата; исходные
данные и созданная полная/частичная копия сохраняются для проверки.

Для непустого мира без манифеста сначала также создаётся полная проверенная
копия. Затем публикуется отдельный `mcsa-storage.json`: только номера
раскладок и идентификатор копии. Он не присваивает игровую версию или реестр
неизвестному миру. Повторный запуск доверяет этой локальной записи; наличие
и целостность архива повторно не проверяются. Неподдержанная или повреждённая
запись допуска останавливает запуск. Публикация не перезаписывает неожиданно
появившийся файл.

Отсутствующий или пустой мир на этом этапе не создаётся и не копируется.
Поэтому после первого наполнения новый мир при первом перезапуске получит
один дополнительный снимок и запись допуска; следующих повторных копий
из-за этого формата не будет. Требования к файловой системе и существующим
замкам остаются теми же, что у механизма снимков выше. Для неподдержанной
платформы/файловой системы автоматическое обновление явно недоступно.

Старые сборки не обязаны читать новые5/11; для отката нужна полная исходная
копия. Запуск постоянного preview-профиля26.3, конвертация между игровыми
версиями и автоматическое восстановление этой работой не разрешаются.

Проверка реализации:2974Rust-теста успешно,85пропущено; Clippy с запретом
предупреждений прошёл. Тесты используют настоящие временные файлы для
снимков, повторного запуска, сохранения старых байтов при отказе и чтения
предыдущих раскладок. Они не моделируют физическую неисправность накопителя.
Отдельный запуск двух настоящих бинарников подтвердил: старый чанк4
сохранён в точной полной копии, изменённый чанк записан как5, повторный
запуск не делает второй бэкап. Повреждённая и будущая запись допуска
останавливают процесс до наблюдаемого слушателя, байты мира сохраняются.
Чанк загружался обычной командой `forceload`, затем менялся через `setblock`.
Первая проба без загрузки чанка получила ожидаемый отказ `setblock` и
сохранена как ошибка подготовки. Игрок не подключался: сетевой переход
playerdata10→11 этой пробой не заявляется, его покрывают файловые тесты.

Воспроизведение: `python tools/check_storage_upgrade.py` показывает план.
Запуск требует `--run --old-binary <старый бинарник> --old-sha256 <SHA256>
--new-binary <новый бинарник> --new-sha256 <SHA256> --output <новая папка>`.
Используется отдельный порт26048. Проба проверяет переход нашего chunk4→5;
пути к бинарникам и их контрольные суммы задаются явно.
